# 开发、审查与本地 Git 流程

## 1. 仓库和工作区

唯一目标：`C:/Users/lishi/code/ravel`。Supervisor记录当前分支和MAIN_BASE_SHA。集成分支固定 `cc/ravel-premium-v1`；任务分支 `cc/Txx-<任务卡slug>`；worktree放 `C:/Users/lishi/code/ravel-worktrees/integration`、`Txx`、`review`、`candidate-Txx`。Linux下映射实际同一提交图；路径写入BASELINE。已存在路径/分支先读取和恢复，不覆盖。

从当前已提交main建立集成分支：`git worktree add -b cc/ravel-premium-v1 <integration-path> <MAIN_BASE_SHA>`。每task由最新已集成SHA建立worktree。原工作区有用户改动时保持原样，禁止自动stash、reset --hard、git clean、强行checkout覆盖、强删分支或删除volume。工作区改动影响同一目标功能时记录冲突，不能自动推断“用户不需要了”。

T02允许fetch固定官方上游对象；不自动pull main，不跟随移动的远端HEAD。其后全部本地操作；本包没有授权push、远端tag、GitHub Release或公开部署。

## 2. 派发与文件锁

Supervisor最多派发3个实现任务，加1个独立Reviewer。每task必须持有自己的写路径白名单。共享文件包括 `src/ravel/config.py`、`domain/enums.py`、`state/tables.py`、`state/mapping.py`、`state/guards.py`、`state/migrations/**`、`gateway/app.py`、`mcp/registry.py`、`pyproject.toml`、Makefile、JS workspace manifest/lockfile及CONTRACTS/schema。

派发前将每task白名单展开成具体路径并登记独占拥有者；两个写路径模式相交（包括目录通配和尚未创建的同名文件）就不能同时写。若任务卡路径过宽，Supervisor须在派发记录细化不重叠子路径后才能并行。只有独立新模块、独立测试文件且无公共文件写冲突，才允许同时实现；最大3不意味着必须凑满3个。

共享文件采用独占批次：Subagent提交变更请求，Supervisor在FILE_LOCKS授予具体路径/任务/分支，其他任务暂停编辑这些路径；获得者完成并提交后由Supervisor集成/释放。锁不会因Agent沉默而过期；Supervisor确认Agent停止写入且工作区状态已保存才能回收。没有锁的任务可阅读、开发自身独立模块和测试，不得预写共享patch等待偷偷合并。

所有新migration由当前持锁任务按唯一Alembic revision追加；不改已应用migration。Supervisor在每次集成检查单head；冲突用单独merge migration或重写尚未发布的新revision，理由和测试入日志。SQLAlchemy表约束、migration及schema必须一致。

## 3. Commit

Subagent只在自身分支commit，格式 `feat(T09): enforce Slurm submission identity`、`fix(T09): reconcile unknown scheduler response`、`test(T09): cover lost submission response`、`docs(T09): record execution evidence`。一个commit一件可解释的事，不把格式化全仓与功能混在一起。

提交前运行 `git diff --check` 和任务规定的检查，确保没有.env、凭据、客户数据或大二进制。禁止把测试失败的中间commit描述成已完成；允许提交中间进度，但候选HEAD必须完整且干净。无变化就写ALREADY_SATISFIED证据，不制造空commit。

tasklogs/Txx由该Subagent拥有；全局状态文件只由Supervisor写。任务交接必须给base_sha、head_sha、changed_files、AC证据、准确测试命令/exit、known issues和共享文件锁情况。

## 4. 独立 Review

Reviewer在固定候选HEAD创建detached worktree，读取任务/契约/日志和完整相关diff；不与作者共用可变工作目录。Reviewer可以跑测试但数据库suite仍必须经过全局测试锁；不可修改实现以让测试通过。

输出使用TEMPLATES/review.json：candidate_sha、base_sha、source_digest、AC逐项结果、findings（文件/行/触发条件/影响/要求修复）、decision。任何未解决的需求违背、权限漏洞、数据丢失、科学证据混淆、未跑必需测试或空实现均CHANGES_REQUESTED。风格建议标advisory，不能扩张本包范围。

作者修复并commit后重新Review。三轮仍不通过时Supervisor先做根因分析、缩小变更或拆子任务；验收标准不降低。只在发现不可由本包决定的重大设计冲突时问用户。

## 5. 集成顺序（不可省略）

1. 确认任务依赖DONE、候选分支干净、作者已交接、第一轮Reviewer APPROVE。
2. 从最新集成SHA建立临时candidate分支/worktree，`git merge --no-ff <task-branch>`；冲突由Supervisor逐项修复并commit，禁止整目录ours/theirs。
3. 在这个集成候选运行任务门禁及受影响回归；schema/执行状态/权限/公用脚本变化还运行对应旧suite。数据库测试串行。
4. Reviewer复核集成候选（尤其冲突修复）及准确source digest；未批准不更新集成分支。
5. 集成分支 `git merge --ff-only <candidate-branch>`，更新PROGRESS/DEVLOG/ROADMAP并commit；只有这时任务DONE。
6. 若期间集成分支被推进，重新生成candidate并重做受影响检查；禁止强推以覆盖。

Supervisor自身写的集成修复没有自审例外。

## 6. SHA 与日志造成的自引用

Review和测试同时绑定实际commit SHA与source_digest。source_digest由T01实现：对Git已跟踪的路径、mode、blob id排序后计算SHA256；只排除明确的进度/执行记录文件：`docs/premium/PROGRESS.json`、`PROGRESS.md`、`DEVLOG.md`、`FILE_LOCKS.json`、`BLOCKERS.md`、`tasklogs/**`、`reviews/**`、`evidence/**`、BASELINE.md、ROADMAP_STATUS.md、INTERNAL_ACCEPTANCE.md、FINAL_REPORT.md、RELEASE_MANIFEST.json、PACKAGE_CHECK.json、PACKAGE_MANIFEST.json、完整任务书_汇总.md。所有这些文件名均相对于docs/premium；除上述列表无其他排除。SPEC、CONTRACTS、TASKS、GATES、实现、测试、依赖、schema、prompt、部署配置均不能排除。

追加纯记录commit不触发全量测试重跑；产品或规范digest变化就使旧批准失效。日志保存被测SHA，后续日志commit不伪装成被测SHA。人工结果manifest自身hash不放进自己的字节里，外层运行索引记录它的hash。

## 7. main 合并与后续修复

T23只有internal全PASS、T00–T22全部DONE、Reviewer最终APPROVE、main仍是记录的baseline且原工作区干净才可 `git merge --no-ff cc/ravel-premium-v1` 到本地main。若main已前进，先将新main合入临时候选并重新Review/受影响回归，重新记录baseline；禁止reset main。

main合并前后核对source_digest一致；main新增merge commit而源码完全相同不重跑昂贵live suite，只保存ancestor/tree核对和diff检查。推进integration为新main后，T24–T29的修复继续任务分支流程。最终gate绑定最终源码digest。无代码变化的外部证据commit只需Reviewer核验真实性。

回退使用独立修复分支或经Review的 `git revert -m 1 <merge-sha>`，不删历史。任何涉及数据库/外部动作的回退先核对兼容性，不能把Git回退当实验/发信/计算已撤销。

## 8. 恢复上下文

会话中断后Supervisor依次读PROGRESS.json、ROADMAP、DEVLOG末尾、FILE_LOCKS、最近Review、git status/worktree list。对RUNNING任务询问实际Agent/检查分支，不重建相同任务或清空进度。资源解锁后仅重跑受影响gate；source_digest或环境版本变化必须说明重跑范围。

T03把以下语义转为项目schema与接口示例，不能另行猜测。字段可以复用现有名称，但映射必须逐项列出；不能借改名删语义。

## 1. 标识、时间与真实性

Project/node/contract/artifact/source沿用现有稳定ID。新Action/attempt/message等用UUID；版本单调整数；API时间UTC RFC3339，日志可同时显示+08:00。文件哈希为SHA256、字节长度整数；参数需单位；费用使用CNY定点decimal字符串。UNKNOWN不能转换成0、空PASS或科学失败。

证据执行类型枚举：RESEARCH_SOURCE、COMPUTATION、HUMAN_LAB、SIMULATED。Claim类型FACT、INFERENCE、HYPOTHESIS。导入历史类型字段时保存原record与新投影的对应，不回写篡改历史真实性。

## 2. 租约与权限上下文

Lease字段：project_id PK、owner_instance_id、epoch、expires_at、renewed_at。首次epoch=1；接管原子增加epoch；数据库时间比较expiry；owner+epoch匹配才续租/释放。

服务端工具调用scope包含project_id、agent_role、binding_id、owner_instance_id、lease_epoch。role和project来自可信runtime binding或Gateway Principal，不来自LLM参数。旧DSH每(project,role)进程的MCP环境可以载可信binding ID；该binding在PG中必须绑定签发时的owner和epoch，每次校验它们仍匹配当前租约。新owner接管必须撤销旧binding并建立新binding；严禁把旧binding自动升级为当前epoch，否则失效Agent会重新获得权威。Gateway用户审批读取用户membership，不能凭产品Agent租约充当人类Owner。

T04把fencing检查放在所有会产生科研/执行副作用的确定性入口，包括turn dispatch、Master mutation和execution start；仍在运行的外部作业需要核对，不能因租约接管重复执行。

## 3. Action 与审批

Action：id、project_id、kind(COMPUTE_SUBMIT/MAIL_SEND/LAB_HANDOVER/SANDBOX_EXEC)、payload_hash、payload_artifact_ref、contract_id/version、requesting_binding、target_ref、required_approval_ref、envelope_version、budget_reservation_ref、expires_at、status、created_at、attempts。

状态：DRAFT→AWAITING_APPROVAL→READY→CLAIMED→ACCEPTED→COMPLETED；不需要人工审批但符合Envelope的Action可从DRAFT校验至READY。REJECTED/EXPIRED/CANCELLED是终止状态；CLAIMED发生网络/进程不确定进入UNKNOWN，核对后进入ACCEPTED或FAILED_CONFIRMED。需要重做已终止/改变payload的动作必须新Action并引用prior_action_id。MAIL的UNKNOWN投影名UNKNOWN_DELIVERY。

Approval绑定payload_hash、contract/envelope版本、完整to/cc/bcc与附件hash、cost upper bound、expiry及人类principal。每次执行前重新鉴权；成员撤权后已批准但未执行的Action不能执行。expire默认24小时。Action唯一执行claim用数据库原子CAS，不靠进程map。Action ACCEPTED仅表示外部系统接受，不等于科学成功或邮件到达对端。

预算预留必须先于外部submit；unknown保留预留。实耗大于预估时记真实值与超额事件，暂停新提交，不改小账目。成本未知保留资源时数和UNKNOWN，不自称硬费用保证。若site只能给资源数，则强制资源时数上限并在UI说明费用未核实。既有Compute/实验入口和新增邮件/沙箱入口都必须接入同一Action/Authority检查；旧start_execution不能成为绕过审批、配额和租约的后门。T06完成既有入口接线，T09/T11/T17/T19各自验收调用链。

## 4. HPC Target 与计算包

Target：id、kind=SLURM_SSH、host/port、username、known_hosts_ref、credential_ref、partition/account、remote_root、allowed_software、max_jobs、cpu/gpu/hour_limits、enabled。敏感ref只在执行进程解析。JobRequest复用WorkBackend接口；新增target_id/manifest_ref，不把host/password拼进模型工具参数。

submission_key=hash(project_id,node_id,contract_version,attempt)。外部reference必须绑定target，不能用可猜JobID越权取消。sbatch返回不确定必须先核对远端记录、队列与accounting；无法查清为UNKNOWN。记录Slurm状态原文和规范化状态，保留ExitCode/原因。

calculation_manifest至少包含contract版本、source/evidence refs、inputs+hash、软件版本和执行环境digest/模块、参数与单位/seed、resource request、required_outputs、stop_conditions、物化器版本。RASPA具体温压、力场、结构和容差由真实Research/冻结contract确定，不由开发者硬填通用默认。

## 5. 实验人员事件

LabHandover复用Phase11模型，补充actor、protocol_version、sample_id、SOP_ref、负责人确认、event_type、reported_at、原始output ref。事件ACKNOWLEDGED/START_REPORTED/DEVIATION_REPORTED/OUTPUT_UPLOADED/STOP_CONFIRMED均明确person-reported。系统withdraw只改变交接状态，不产生STOP_CONFIRMED。实验物理执行不由Dev Agent或自动测试完成。

## 6. Mailbox、邮件与发送

Mailbox：id、owner/project授权范围、imap_host/port/TLS、smtp_host/port/TLS、username、credential_ref、fixed_from、recipient_allowlist、enabled；默认不允许明文连接或任意SMTP端点。

MailMessage：id、mailbox_id、imap_uidvalidity/uid、message_id、references/in_reply_to、thread_id、project_id(nullable)、raw_eml_artifact、attachments、content_hash、trust=EXTERNAL_UNTRUSTED、received_at。UNASSIGNED由用户绑定，绑定需项目权限并审计。MIME正文是内容，不能被解释为Owner的系统指令。

SMTP发送状态：DRAFT→APPROVAL_PENDING→APPROVED→SENDING→ACCEPTED；失败已确认可FAILED_CONFIRMED，DATA发起后任何不确定为UNKNOWN_DELIVERY。Message-ID固定并帮助核对，但不能承诺SMTP服务端据此去重。SENDING进程重启先进入UNKNOWN，人工/可靠provider核对后再决定；不会自动回队重发。对端收件确认与SMTP ACCEPTED分字段。

T16/T17内部使用真实协议测试服务；其发信只能送隔离服务。T27外部账号必须operator明确授权收件人并设置LIVE_ENABLE，不能因有SMTP凭据就任意外发。

## 7. SandboxProvider

`provision(project_id, authority, limits)->handle`；`reconnect(handle, authority)->handle`；`execute(handle, argv, cwd, env_refs, timeout, action_id)->run_ref`；`status(run_ref)`；`cancel(run_ref)`；`files.list/read/write(handle, relative_path)`；`stop(handle)`；`destroy(handle)`；`collect(run_ref)->artifact_refs`；`capabilities()`。接口需typed schema，命令优先argv；shell脚本本身是受审计输入产物而非字符串拼接。

Handle：id/provider/project_id/epoch/capabilities/state；secret不在handle。生命周期PROVISIONING→READY→STOPPED/DESTROYED/FAILED；VM池AVAILABLE→LEASED→QUARANTINED，重建确认才重新AVAILABLE。VM部署仅operator预配，host key验证，单项目独占。缺能力返回UNSUPPORTED，不偷偷降级在host执行。默认资源和网络限制见T19。

## 8. Gateway v1 API 与事件

保留已有API供TUI使用；新增/v1适配路径：

| 路径 | 方法/行为 |
|---|---|
| /v1/auth/login、refresh、logout | POST；沿用既有会话语义与membership，不让前端持harness凭据 |
| /v1/projects | GET分页、POST创建项目；创建不直接写科学DAG |
| /v1/projects/{id}/snapshot | GET；聚合状态与anchor_seq，读一致性快照 |
| /v1/projects/{id}/conversation | GET分页、POST给Master消息；client_message_id防重复 |
| /v1/projects/{id}/dag | GET只读 |
| /v1/projects/{id}/sources、/evidence、/computations | GET分页及单条详情；source读取有bounded range/page |
| /v1/projects/{id}/actions | GET；approve/reject采用POST /actions/{action_id}/approve或reject，payload_hash必填 |
| /v1/projects/{id}/authority-envelope | GET/POST新版本；复用现有授权 |
| /v1/projects/{id}/pause、resume | POST；权限和lease协调 |
| /v1/projects/{id}/lab/tasks | GET；下载包/签收/偏差/按required_output上传复用已有服务 |
| /v1/projects/{id}/mail | GET；草稿POST；approve/send仅通过Action；未知结果人工核对单独审计 |
| /v1/projects/{id}/events?after_seq=N | WebSocket；项目内有序，首次snapshot或replay |

所有列表limit默认50、最大100，稳定cursor。Action、mail、lab等单条操作都从resource id回查project，不仅相信URL。API错误统一 `{code,message,request_id,details}`；典型code=FORBIDDEN/STALE_VERSION/APPROVAL_REQUIRED/BUDGET_EXCEEDED/RESYNC_REQUIRED/UNKNOWN_EXTERNAL_RESULT/UNSUPPORTED。

Event：id、project_id、seq、type、aggregate_id/version、occurred_at、payload。seq在project内单调且与snapshot anchor一致；重连可重复返回已送事件但不能漏，客户端按seq去重。cursor超保存窗需RESYNC_REQUIRED；snapshot+replay取一致边界。权限重检<=5秒。前端失败重试不得重复创建消息或Action。

## 9. 证据与 gate 结果

任务状态只用TODO/READY/RUNNING/REVIEW/FIX_REQUIRED/INTEGRATING/DONE/BLOCKED_EXTERNAL/BLOCKED_USER_INPUT。ALREADY_SATISFIED为实现结论字段，不是绕过Review的任务状态。

gate row只用PASS/FAIL/BLOCKED_EXTERNAL/MISSING。pytest SKIP/XFAIL必须转FAIL，唯一例外是明确缺少外部资源且该行预先分类external，转BLOCKED_EXTERNAL。内部必须的Linux/Docker环境缺失即internal gate不通过。

项目工程状态：IN_PROGRESS、INTERNAL_READY_EXTERNAL_PENDING、INTERNAL_READY_EXTERNAL_BLOCKED、PARTIALLY_CERTIFIED、FULLY_CERTIFIED。旧 `make release-gate` 保留CERTIFIED/PARTIALLY_CERTIFIED/NOT_CERTIFIED和非零规则；仅全部旧新行PASS才能映射FULLY_CERTIFIED。

# 验收门禁与证据规则

## G0 接管

T00保存实际目录/HEAD/dirty/worktree/remote，完整任务与日志存在，Reviewer批准。没有授权重置原目录或覆盖未提交变更。当前观察值是记录，不是执行时强制回退目标。

## G1 单任务

除T00/T03文档与T02引入门禁外，每代码任务在 `tests/premium/Txx/` 提供必要行为验证；各AC必须映射到具体测试nodeid或真实操作证据。`make premium-task TASK=Txx`运行映射命令、diff检查、该任务静态检查与受影响旧suite。代码必须已commit且干净；默认无SKIP/XFAIL/MISSING。不能为了满足数量复制实现逻辑写空测试。

T01创建：premium-preflight、premium-task、premium-source-digest；T22创建：premium-gate、premium-gate-plan、premium-live。文档里的命令是待实现接口，runner输出与Makefile必须一致。源代码digest算法见ENGINEERING_PROTOCOL。

## G2 基线与受影响回归

既有入口仍有效：make lint、make test-unit、完整tests/integration目录、tests/e2e、make acceptance、make phase10-acceptance，以及T02后make phase11-acceptance、make release-gate。全量内部测试由inventory按具体nodeid执行，不能简单使用 `-m not live` 假设标记完备。

legacy-inventory必须包含收集到的每个nodeid；每个外部分类说明为何需要真实模型/Internet/HPC/真人及原测试ID。Reviewer核对分类，防止把代码故障重分类成外部阻塞。旧 suite 包含live项时保留原命令的非零/skip日志，并由inventory给逐项internal结果，禁止把整套失败描述成PASS。

改domain/state/migration/权限/执行合同/共享脚本必须运行所有相关旧阶段与新task suite；其他独立UI改动可仅跑UI相关回归。完整internal gate在T23统一跑一次；失败修复后重复受影响行，最终manifest不得混用不同source digest的结果。旧release-gate要求真实模型等资源时记录BLOCKED_EXTERNAL，不篡改脚本为成功。

## G3 集成候选

Task branch APPROVE后先合临时候选，跑门禁并由Reviewer审合并后的真实tree，再推进integration。共享测试库串行。产品源码改变重新绑定Review与测试；只追加进度/测试记录不做无意义全量重跑。任何未解释回归都阻塞集成。

## G4 Internal

`make premium-gate PROFILE=internal` 必须覆盖：全部已分类legacy deterministic项目；所有T04–T22内部AC；迁移空库/升级/单head；Python静态类型；生成客户端一致性；TypeScript类型和构建；真实Electron安全及Windows打包启动；真实PG/Temporal/MinIO；协议级IMAP/SMTP隔离服务；真实Docker隔离；跨项目权限/租约竞争/Action版本/资源竞争/重启及不确定外部结果。

模拟Slurm和模拟实验人员可证明内部软件链，但输出显著SIMULATED；它们不会通过任何真实HPC/真人测量行。缺Docker/Linux不能因为属于环境问题就让internal变绿。

T23代码完成并本地main合并的条件是G4全部PASS且Reviewer最终批准。此时外部项可BLOCKED_EXTERNAL，整体只叫内部就绪。

## G5 Certified

`make premium-gate PROFILE=certified` = G4 + 真实DSH五角色/真实Research + T24腾讯云/COS + T25真实HPC/RASPA + T26真人实验 + T27真实邮箱 + T28真实VM + T29同Project科研闭环。并且原make release-gate无skip/缺资源行、真正CERTIFIED。

live入口 `make premium-live TASK=T24` 等必须先检查operator授权、测试资源allowlist、预算/有效时间和必需配置；缺少条件在任何副作用前退出非零。真人实验行的自动程序只核验真实人员上传的证据，不能自动执行实验或替真人签名。真实Research不能用fixture，允许unit parser用fixture。

若external条件不满足：内部PASS且外部blocked→PARTIALLY_CERTIFIED；任一实际错误→未通过。没有FULLY_CERTIFIED例外。

## 证据manifest

每次运行 `evidence/Txx/<run-id>/manifest.json` 至少：run_id、task_id、AC映射、北京时间与UTC、source_commit、source_digest、platform、依赖/软件版本、命令、cwd、exit_code、junit_path、log_path、artifacts[{ref,sha256,size}]、data_mode(REAL/SIMULATED/MIXED)、external_resources（非秘密ID）、operator_authorization_ref、result、blocked_reason。

不伪造签名：operator确认保存真实确认文本/签名文件及hash，自动化只能核验存在性、关联与文件完整性；物理测量正确性由产品Review/实验负责人评估。邮件证据要包含对端接收确认，SMTP250本身只证明服务器接受。HPC证据需要真实JobID/调度输出，不能仅manifest里一个自填数字。

大二进制留受控Artifact Store/本地evidence volume，Git保存索引与hash。必须在报告说明哪些文件受控保存、怎样由授权人员复核。所有秘密必须脱敏，原始敏感输出不打包进公开构建。
