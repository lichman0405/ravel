## 实现

1. `src/ravel/backends/slurm/targets.py`（新增）
   - `HpcTarget` 与 `schemas/premium/hpc_target.schema.json` 逐字段对应：`target_id`（UUID）、`kind=SLURM_SSH`、host/port/username、`known_hosts_ref`、`credential_ref`、`remote_root`、`allowed_software`、`max_jobs`、`enabled`，可选 partition/account/cpu/gpu/hour 限制。
   - 未知字段、缺字段、非 allowlist id、disabled target 均拒绝；partition/account 只接受单 token，`remote_root` 只接受绝对 POSIX 路径且不能含 `..`。
   - `TargetRegistry` 只回答构造时给定的 id；`resolve_target`/`resolve_enabled` 是唯一把 `env:`/`file:`/`key:`/`keyfile:` 引用变成凭据的函数，只在执行进程调用。`known_hosts_ref` 只允许 `file:`。`ResolvedCredential`、`SlurmTarget` 的 repr 均脱敏。
   - `parallel_quota(project_quota, target_max_jobs) = min(T06 每项目配额, target.max_jobs)`；两者都不能被放大。
2. `src/ravel/backends/slurm/backend.py`
   - target 模式按请求的 `target_id`（或显式默认 target）选择固定目标；未配置 id 在接触网络前拒绝。
   - 提交键复用 T06 `compute_submission_key(project, node, contract_version, attempt)`；target 模式的 job ref 带 target token、job id 和 digest。
   - 提交前读取远端 submission record：文件不存在才继续；读取失败是 transport fault；存在但不可解析/字段不符/状态未知一律 `UNKNOWN`，不重发 `sbatch`。`SUBMITTING` 记录先查 squeue + sacct；只有两处都确认不存在且超过 grace 窗口才允许一次提交；响应丢失但 job 可见时采纳该 job。
   - submission record 状态为 `SUBMITTING`/`SUBMITTED`/`REJECTED`；record 绑定 project/node/attempt/contract 版本/submission key/digest/target id，不写凭据。
   - 目录和文件安全：entrypoint 必须是 workspace 内相对 POSIX 路径，拒绝绝对路径、反斜杠、空/`.`/`..` 段、entrypoint 路径上的 symlink 和 workspace 内任意 symlink/特殊文件；上传只传常规文件；采集的 remote directory 必须位于 target `remote_root` 之下。
   - 采集要求 target 有 object store；收集 JobID、slurm state、ExitCode、Elapsed、MaxRSS、AllocTRES、原始 scheduler log、manifest 文件列表和缺失输出；未报告的计量字段写 `UNKNOWN`，绝不写 0。
   - 取消新增 `cancel_with_state`：只接受同 project 且同 target 的 ref，状态含 `CANCELLED`/`ALREADY_TERMINAL`/`UNKNOWN_JOB`/`REFUSED_SCOPE`/`REFUSED`。
   - 明确异常状态：`SlurmSubmissionUncertain.state=UNKNOWN`、`SlurmStateUnknown.state=SACCT_DELAY`、`PARTITION_REJECTED`、`ACCOUNT_REJECTED`、`REJECTED`；拒绝记录持久化后再次提交不再询问 scheduler。
3. `src/ravel/backends/slurm/ssh.py`
   - target 模式只加载目标自己的 `known_hosts`，固定 `RejectPolicy`；不存在 target 模式的 auto-add opt-in。
   - `HostKeyVerificationError.state` 区分 `HOST_KEY_UNKNOWN`（未记录/文件不可读）与 `HOST_KEY_MISMATCH`（密钥变化）；认证失败是普通 transport error，不伪装成 host-key 状态。
   - 所有离开 backend 的字符串经 `Redactor`；`Redactor` 自身的 repr 也不打印 secret。
4. `src/ravel/execution/backends.py`
   - `ParallelSubmissionCoordinator` 只提交 `NodeStatus.READY` 且依赖完成、Review 允许、预算允许的节点；`SUBMITTED` 和 `UNKNOWN` 占用 slot，`REFUSED`/`NOT_READY` 不占用；超过 quota 返回 `QUEUED`，`release` 后下一次 pass 可提交。
   - `resolve_uncertain` 必须由调用者给出观测结果（job id 或确认不存在）才释放 UNKNOWN slot。
   - `join_required` 只等待调用者点名的 required 节点，返回每个 required 状态；缺 handle 或超时为明确错误。
5. `scripts/run_temporal_worker.py`
   - 新增 `--slurm-targets-file`、`--slurm-default-target`；target 文件在 worker 启动时校验。
   - `_target_mode_backend` 是本进程唯一解析凭据的位置；banner 只用 target document（引用，不含 secret），显示 target id/user@host:port 和默认 target。
   - 多个 enabled target 且未显式给默认值时，请求必须自己命名 target，避免 allowlist 顺序决定花哪个 allocation；无 enabled target 或默认值不在 enabled 集合时启动失败。
   - 旧的单目标 Slurm 配置和命令面保持不变。
6. 测试 `tests/premium/T09/`

## 已知边界与缺口

- **真实 HPC 未认证（BLOCKED_EXTERNAL）**。解锁条件：可达的 Slurm-over-SSH 登录端点；operator 核验并可由 worker 读取的 known_hosts 文件；执行进程可解析（env/file/key）且不在模型 prompt/仓库中的凭据；与集群 partition/account/remote root/软件目录匹配的 allowlist target id；`--submit` 时的一次短分配授权。真实认证属于 T25。
- **并行协调器与生产 loop 的关系**：`ParallelSubmissionCoordinator`/`join_required` 是 backend 级策略/测试工具；生产 Supervisor 通过 `ProjectLoop._executor_starts` 的 quota 信号量并发启动 seat，T06 ActionService 仍是资源权威。两者都用 T06 的 `action_compute_per_project` 与 target `max_jobs` 的同一数值。
- **quota 由调用者提供**。协调器不直接读 BudgetService，避免形成第二套预算解释；测试验证了 T06 设置与 target 上限的组合函数，生产接线必须传入相同结果。
- **采集依赖远端 manifest**。只拉取远端 `*_manifest.json` 中 `required_outputs` 点名的文件和 scheduler 日志；没有 manifest 时不猜测必需输出，只返回目录/记录说明。该行为由 AC4 测试覆盖，但真实站点 manifest 生成属于 preparation 下游任务。
- **计量字段依赖站点 sacct**。target 模式请求 `AllocTRES`/`MaxRSS`/`Elapsed`；缺失或命令失败一律 `UNKNOWN`。不同 Slurm 版本的 accounting 插件未在真实集群验证。
